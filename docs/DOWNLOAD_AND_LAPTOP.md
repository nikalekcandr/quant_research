# Докачка данных и подготовка ноутбука под поиск альфы

Короткий ответ на три вопроса:

1. **Докачивать — да, но не всё подряд.** Порядок важности: (а) свежие часовые лесенки Kalshi,
   (б) спот + фандинг + DVOL до сегодняшнего дня, (в) перпетуал (без него базис не измерить), (г) макро-календарь.
   Ноябрьскую ленту и глубину стакана **докачать нельзя** — они пишутся только вперёд.
2. **Ноутбук готовить надо, но не ради скорости.** Главное — не дать машине спать и не потерять живую ленту;
   всё остальное (venv, планировщик, логи) — это полчаса работы.
3. **Имеет ли это смысл?** Как «ещё данных → ещё альфы» — почти нет: мощности уже хватает (см. §8),
   узкое место — исполнение и устойчивость эффекта, а не объём истории. Как «не потерять живые данные,
   которых потом не будет» — да, и это единственная необратимая часть.

## 1а. Обновить код за секунды (вместо архива на 350 МБ)

В репозитории рядом лежат вещи очень разной природы: **~2 МБ кода** (`src/`, `studies/`, `tests/`, `docs/`)
и **~375 МБ уже скачанных данных** (`data/raw`, `data/interim`, `results/*.parquet`). Архив с GitHub тянет
всё вместе, поэтому после каждой правки вы качаете и распаковываете сотни мегабайт данных, которые у вас
уже есть и которые всё равно берутся не из git, а с бирж.

`scripts/get_code.py` качает только код. Три способа запустить одно и то же:

- **двойной клик** по `update_code.bat` в корне папки (Windows) — «одна кнопка»: сам находит
  `.venv\Scripts\python.exe`, печатает список изменённых файлов и ждёт нажатия клавиши;
- `./update_code.sh` — то же для macOS/Linux;
- из консоли:

```bash
python scripts/get_code.py --dry-run     # что изменилось бы, ничего не пишется
python scripts/get_code.py               # обновить (ветка main)
python scripts/get_code.py --branch arena/d0527b61-quant-research   # другая ветка
python scripts/get_code.py --http        # без git: через GitHub API (только изменённые файлы)
```

Что внутри:

- **git-путь (по умолчанию, если git установлен).** Забирается только дерево ветки
  (`git fetch --depth 1 --filter=blob:none`, ~0,5 МБ), затем пишутся **только те файлы, что отличаются** —
  сравнение идёт по git-хешу блоба (`sha1("blob <len>\0" + содержимое)`), поэтому «уже актуально»
  определяется точно, без индекса и без `git checkout`: содержимое берётся объектом (`git cat-file blob`)
  и пишется байт-в-байт. Это же снимает windows-специфику — CRLF-преобразования и записи в индекс, на
  которых `git checkout` в папке из ZIP может отказать. Работает и в распакованной из ZIP папке: скрипт
  один раз делает `git init` и запоминает remote, дальше это 0,5–5 секунд на запуск.
  Что мы записали в прошлый раз — лежит в `.code_sync.json`; по нему же скрипт отличает вашу правку от
  свежего изменения на GitHub и отказывается затирать вашу, пока нет `--force`.
- **http-путь (`--http`, если git нет).** Один запрос за деревом файлов, потом параллельно (8 потоков)
  только изменённые файлы с `raw.githubusercontent.com`, с fallback на contents API; каждый файл проверяется
  по хешу.
- **`data/raw`, `data/interim`, `results/*.parquet`, `reports/` не скачиваются никогда** — это данные, их
  источник — биржи, а не git. Из `results/` берутся только текстовые отчёты `results/studies/*.md`.

Замеры на реальном репозитории: первый прогон — **48–50 с, 160 файлов, 2,1 МБ** (против ~350 МБ архива),
повторный прогон без изменений — **0,5 с**, после одной моей правки (11 файлов) — **4–5 с**.
Локальные правки скрипт не затирает: если файл изменён вами, он откажется и попросит `--force`.

Если что-то пошло не так, скрипт теперь печатает **stderr самого git** и выходит с кодом 1, ничего не
записав (раньше ошибка `git checkout` приходила без текста и выглядела загадочно). Полезное:

- `fatal: couldn't find remote ref` — опечатка в `--branch`;
- отказ по сертификату (корпоративный прокси) — `QRR_CA_BUNDLE=C:\certs\ca.pem`;
- если git ведёт себя странно в этой папке — `python scripts/get_code.py --http` (GitHub API вместо git,
  тот же список файлов, проверка по хешу).

Ветка: по умолчанию `main`, но чужие ветки тоже можно — `--branch arena/d0527b61-quant-research`
(или переменные окружения `QRR_REMOTE` / `QRR_BRANCH`). Если ноутбук за корпоративным прокси и `https`
ругается на сертификат — укажите файл CA: `QRR_CA_BUNDLE=/path/to/ca.pem python scripts/get_code.py`.

## 2. Порядок докачки

### Одной командой (рекомендуется)

```powershell
python scripts/night.py            # поставить в фон и пойти спать
python scripts/night.py --dry-run  # сначала посмотреть план: что и сколько будет качаться
python scripts/night.py --status   # утром: что скачалось, что упало, что осталось
```

То же самое двойным кликом: `scripts\night.bat`. Скрипт сам решает всё, что раньше приходилось помнить:

- **окно.** Kalshi качается с 2025-12-01 (там начинается история репозитория; до 18.03.2026 у биржи была
  другая сетка страйков — $250 вместо $100, то есть другой контракт). Файл `data/manual/starts.json` с
  датой 2024-12-12 больше не заставляет ночь копать два лишних года; `--since` его перекрывает.
- **темп.** Один общий адаптивный лимитер: на 429 ждут все потоки, пауза растёт и потом сама спадает.
  Kalshi идёт в 6 потоков.
- **порядок.** Сначала дешёвые источники (минуты), последним Kalshi (часы) — если ночь окажется короткой,
  нужное для панели всё равно на диске.
- **устойчивость.** Падение источника не останавливает остальные; падение дня Kalshi не роняет источник;
  недокачанное подберёт следующий запуск.
- **отчёт.** `logs/night-<дата>/summary.md` (таблица «источник / статус / время»), `state.json` (обновляется
  по ходу — видно, где остановился), `run.log` целиком, `audit_before.csv` и `audit_after.csv`.

Экран гасить можно: инхибитор сна ставится автоматически, окно закрывать — тоже (работа идёт в отдельном
процессе). Что нельзя — закрывать крышку и выдёргивать питание, см. §4.1.

### Шаг 1а. Почему Kalshi идёт 50–60 секунд на сутки и как это ускорить

Одна календарная дата — это 24 события (по одному в час). На «живом» событии два запроса: список страйков
(`/markets`) и пачка 1-минутных свечей (`/markets/candlesticks`, до 50 тикеров за запрос) — итого ~48 запросов
на сутки. У архивного события (`/historical`) свечи отдаются **по одному тикеру на запрос**, около 16 страйков
в полосе ±1,5 % от цены, то есть ~400 запросов на сутки. Каждый запрос — это честный round-trip к Kalshi
(~0,6–1,1 с из Европы), и раньше они шли строго по одному. Отсюда 50–60 с.

Теперь сутки качаются параллельно, а лимит вежливости (`--min-interval`, по умолчанию 0,15 с на запрос
суммарно по всем потокам) остаётся общим:

```bash
python -m src.download.update --only kalshi --workers 4          # 4 суток одновременно
python -m src.download.update --only kalshi --workers 8          # если канал и Kalshi не против
python -m src.download.update --only kalshi --workers 1          # старое поведение, строго по порядку
```

Замер на локальном стенде (фейковый Kalshi с латентностью 0,25 с на запрос, 32 запроса):

| потоки | время | ускорение | запросов/с |
|---|---|---|---|
| 1 | 8,2 с | ×1,0 | 3,9 |
| 2 | 4,2 с | ×2,0 | 7,6 |
| 4 | 2,2 с | ×3,8 | 14,8 |

В реальности латентность выше, поэтому сутки на живых событиях — примерно 12–15 с вместо 50–60, архивные
(400 запросов) — 60–90 с вместо 10 минут. Файлы те же самые, побайтово: тест `tests/test_kalshi_workers.py`
сравнивает последовательный и параллельный прогон строка в строку.

**Важно: потоки не отменяют лимит.** Все они делят одну паузу `--min-interval`, то есть суммарно это
`1/min_interval` запросов в секунду (0,15 с → 6,7/с). Выше этого числа `--workers` ничего не ускоряет: узкое
место — вежливость, а не параллельность. Ориентиры:

| что качаем | запросов | 6,7 запроса/с | 16 запросов/с (`--min-interval 0.06`) |
|---|---|---|---|
| одни живые сутки (48 запросов) | 48 | ~10 с | ~5 с |
| одни архивные сутки (~400) | 400 | ~1–2 мин | ~30 с |
| окно июль–ноябрь (≈148 суток) | ~60 тыс. | ~2,5 ч | ~1 ч |
| весь архив с `KALSHI_START` (≈715 суток) | ~286 тыс. | ~12 ч | ~4,8 ч |

Откуда 715 суток, если в `config.py` стоит `KALSHI_START = "2026-01-01"`: файл `data/manual/starts.json`
(его пишет `backfill.py --probe`) перекрывает конфиг и хранит самую раннюю найденную дату — `2024-12-12`.
Перекрыть это можно флагом `--since`: он главнее любого файла.

### Если прилетел HTTP 429

Kalshi (и любой другой venue) рано или поздно отвечает `429 Too Many Requests`. Раньше это было смертельно:
шесть попыток с паузами 1+2+4+8+16+32 секунды, потом исключение — и оно вылетало из пула потоков, **убивая
весь источник** вместе со всеми ещё не скачанными днями. Теперь так:

- **429 ставит глобальный кулдаун.** Паузу держат все потоки, а не только тот, что получил отказ; если сервер
  прислал `Retry-After`, ждём ровно столько (но не больше минуты).
- **Пауза адаптивная.** Каждый 429 увеличивает промежуток между запросами в 1,5 раза (потолок 2 с), после
  50 чистых ответов подряд он постепенно возвращается к заданному `--min-interval`. Один прогон сам
  подстраивается под то, что venue реально терпит.
- **Сбой дня больше не валит прогон.** День помечается как failed, остальные качаются дальше; в конце
  печатается `finished N/M days …, F failed` и список упавших дней. Файл дня либо полный, либо его нет —
  повторный запуск той же команды докачает только упавшие дни.
- **Итог по лимитам** виден в конце прогона: `rate limits: 37 × HTTP 429; the pause between requests widened
  to 0.34 s`.

Практика: для длинного бэкфилла начинайте с `--min-interval 0.06`, а если 429 идут пачками — ставьте
`0.10–0.15` сами, не дожидаясь, пока это сделает адаптация.

Пока идёт закачка, раз в 30 с печатается строка прогресса — по ней видно, что процесс жив:

```
kalshi: 12/715 days done, 8.4 min elapsed, 2140 requests (4.2/s), 1.4 days/min, ETA 8.2 h, 0 failed
kalshi: finished 715/715 days in 11.9 h, 286120 requests
```

Если Kalshi начал отвечать `429`, увеличьте паузу: `--min-interval 0.25`. Код сам делает 6 попыток с
экспоненциальной задержкой, но вежливее — быстрее в итоге.

### Шаг 2. Kalshi — самое долгое, делать в два приёма

Сначала последние недели (это то, что нужно для текущей оценки, — 10–30 минут):

Потом — вся история в фоне (≈80 с на день, ≈50 запросов на день, месяц ≈ 40 минут):

### Если пишет `No module named 'config'`

Это значит, что файл запущен как скрипт из другой рабочей папки, и Python положил в `sys.path` каталог
`src/download/`, а не корень проекта. С 26.11 оба способа работают:

```bash
python -m src.download.update --audit          # из корня проекта
python src/download/update.py --audit          # прямой запуск файла
```

Внутри файлов `src/download/*.py` для этого стоит трёхстрочный bootstrap (`if __package__ in (None, "")`),
который добавляет корень проекта в путь до `import config`. Если вы запускаете из IDE — выставьте Working
directory = корень репозитория и интерпретатор = `.venv/bin/python` (`\.venv\Scripts\python.exe` на Windows);
оба условия теперь необязательны, но с ними любые скрипты проекта ведут себя одинаково.

## 3. Что докачать нельзя (и почему это важнее остального)

| чего нет | почему нельзя | что делать |
|---|---|---|
| Ноябрьские книги до 8 ноября и пропущенные часы 07–10 UTC | логгер писал только то, что успел | только вперёд: поднять `live.py` и не давать машине спать |
| Глубина стакана (размеры на уровнях) | Kalshi отдаёт свечи, а не историю книги | писать снимки **сейчас**: без них не измерить ни adverse selection (T2/T8), ни реальную ёмкость |
| Секундные тики BRTI | историю индекса задним числом не отдают | писать самим; без них не проверить арифметику расчётного среднего (V07) |
| Исполнение мейкерских заявок | в свечах нет очереди | писать книгу + свои заявки, тогда будет fill rate |

Это и есть ответ на «что качать»: **самое ценное — не история, а то, что пишется вперёд**. История Kalshi
перекачиваема в любой момент, а живая книга — нет.

## 4. Подготовка ноутбука

### 4.1 Сон — главный враг

Нужны три вещи: питание, запрет сна, автозапуск.

**Windows (PowerShell, от администратора один раз):**

```powershell
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 2      # экран гаснет через 2 минуты — это НЕ сон, качалке всё равно
powercfg /change disk-timeout-ac 0
powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0   # закрытая крышка: ничего не делать
powercfg /setactive SCHEME_CURRENT
powercfg /requests                      # кто сейчас держит машину; пусто — никто не держит
```

Смысл в двух разных вещах, которые легко перепутать:

- **Экран погасить — можно и нужно.** Гашение экрана, блокировка (Win+L) и переход в «спящий экран» процесс
  не останавливают. `monitor-timeout-ac 2` гасит подсветку, вычисления продолжаются.
- **Сон машины — нельзя.** Его держит инхибитор (`keep_awake`, `SetThreadExecutionState`), но только от
  простоя. Закрытая крышка — отдельное событие: её надо перевести в «ничего не делать» строкой
  `LIDACTION 0` выше (или оставить крышку открытой). Ноутбук — на зарядку: от батареи Windows всё равно
  уйдёт в сон по своему плану.

**macOS:**

```bash
sudo pmset -a sleep 0 disksleep 0 hibernatemode 0
pmset -g assertions                     # что мешает сну
caffeinate -dimsu &                     # держать сон выключенным, пока живёт процесс
```

**Linux:**

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target
systemd-inhibit --what=idle:sleep --why="live logger" sleep inf &
```

В коде это уже сделано: `src/runner.keep_awake()` теперь ставит инхибитор на всех трёх ОС
(`SetThreadExecutionState` / `caffeinate -i -m -w <pid>` / `systemd-inhibit`), а `src/download/update.py`
вызывает его сам. Проверка: `python -c "from src import runner; print(runner.keep_awake())"`.
Выключить: `runner.keep_awake_off()`.

Важно: инхибитор не спасает от закрытой крышки на macOS (это сон по событию, а не по таймауту) — крышку
держать открытой или использовать `caffeinate -s` при питании от сети.

### 4.2 Планировщик — чтобы данные писались без вас

| ОС | что | команда |
|---|---|---|
| Windows | задача каждые 10 минут | `schtasks /create /tn btcvol-live /tr "C:\...\.venv\Scripts\python.exe C:\...\live_once.py" /sc minute /mo 10 /rl highest /f` |
| macOS | launchd | `~/Library/LaunchAgents/com.btcvol.live.plist` с `StartInterval` 600 и `RunAtLoad` true, затем `launchctl load -w …` |
| Linux | systemd user timer | `systemctl --user enable --now btcvol-live.timer` (готовые юниты — в `deploy/server/`) |

Ежедневная синхронизация истории: `python daily_update.py` (он сам держит lock, пишет логи и пересобирает
таблицы). Ставьте её на 06:20 UTC — это после расчёта 05:00 UTC и до европейского утра.

### 4.3 Диск, память, сеть

* Данные растут на ~1–1.5 ГБ в месяц (сейчас `data/` ≈ 300 МБ без `raw/binance`). 20 ГБ свободного места
  хватает на годы; 5 ГБ — минимум, ниже начинают сыпаться записи панели.
* RAM: 8 ГБ достаточно (панель 3.5 млн строк × 20 колонок ≈ 600 МБ, все исследования — минуты).
* Сеть: не чаще 4–5 запросов в секунду к одному хосту; `update.py` ставит `min_interval=0.25`.
  Kalshi за CloudFront отдаёт 429 при агрессии — тогда просто повторить позже, ничего не теряется.

### 4.4 Git-гигиена

* **Важно:** в этом репозитории версионируется и код, и данные (`.gitignore` так и говорит, и в git уже
  лежит 6 806 файлов `data/raw`, сам клон — 857 МБ). Значит докачанные файлы появятся в `git status` как
  сотни мегабайт. Варианта два: (а) держать как есть — воспроизводимость полная, но клон пухнет;
  (б) добавить `data/raw/kalshi*/` и `data/raw/binance/` в `.gitignore` и хранить их локально — тогда
  репозиторий остаётся лёгким, но у клона не будет ленты без отдельной докачки. Решать вам; в `results/`
  идут только CSV/MD исследований в любом случае.
* Перед длинной сессией: `git pull --ff-only`, после — `git add -A && git commit` с числами в сообщении.
* Исследования детерминированы (сиды в бутстрэпе фиксированы), поэтому повторный прогон должен давать те же
  CSV — это дешёвая проверка, что ничего не «поехало».

## 5. Имеет ли смысл докачивать историю: расчёт мощности

Считаем по факту, а не на глаз (1 контракт, P&L на час, `results/studies/wings_ten_bootstrap.csv`):

| правило | период | часов | ¢/час | σ на час | сколько часов нужно для t=2 при эффекте 2¢ |
|---|---|---|---|---|---|
| W04 (6–10¢, 15–30 мин) | тест сен–окт | 920 | +2.57 | 20.9¢ | **435** |
| W04 | ноябрь | 120 | −5.64 | 34.1¢ | 1 165 |
| W03 (10–20¢, 5–15 мин) | тест сен–окт | 328 | +3.33 | 30.1¢ | 907 |
| W03 | ноябрь | 51 | −5.80 | 40.2¢ | 1 613 |

Что из этого следует:

* **По июлю–октябрю данных уже с избытком**: 920 часов при нужных 435 — то есть точность оценки
  ограничена не объёмом, а тем, что эффект, судя по всему, зависит от режима.
* **Ноябрь мал**: 120 часов, чтобы поймать −5.6¢ нужно ~1 165. Поэтому «в ноябре не работает» — это пока
  отсутствие доказательства работы, а не доказательство поломки. Ещё 2–3 месяца живой ленты закроют и это.
* **Чем даст докачка истории**: интервал W04 на тесте сейчас [1.20; 3.82]¢/час; три дополнительных месяца
  (~2 100 часов) сузят его примерно до ±0.7¢ вместо ±1.3¢. Полезно, но это уточнение уже известного, а не
  новая альфа.
* **Чего не даст вообще**: ответа на вопрос «почему в ноябре минус». На него отвечают не месяцы, а
  (а) глубина стакана (кто сдаёт крыло и по какой цене), (б) базис и фандинг (режим), (в) макро-календарь.

**Вывод.** Докачивать стоит в таком порядке: живая книга с размерами → перпетуал (базис) → Kalshi-история
до сегодня → макро. Первые два пункта дают новые данные, третий — только больше тех же.
