# Докачка данных и подготовка ноутбука под поиск альфы

Короткий ответ на три вопроса:

1. **Докачивать — да, но не всё подряд.** Порядок важности: (а) свежие часовые лесенки Kalshi,
   (б) спот + фандинг + DVOL до сегодняшнего дня, (в) перпетуал (без него базис не измерить), (г) макро-календарь.
   Ноябрьскую ленту и глубину стакана **докачать нельзя** — они пишутся только вперёд.
2. **Ноутбук готовить надо, но не ради скорости.** Главное — не дать машине спать и не потерять живую ленту;
   всё остальное (venv, планировщик, логи) — это полчаса работы.
3. **Имеет ли это смысл?** Как «ещё данных → ещё альфы» — почти нет: мощности уже хватает (см. §8),
   узкое место — исполнение и устойчивость эффекта, а не объём истории. Как «не потерять живые данные,
   которых потом не будет» — да, и это единственная необратимая часть.

## 1. Что где лежит и чем обновляется

| источник | каталог | модуль | что открывает |
|---|---|---|---|
| Binance спот 1 мин | `data/raw/binance` | `src/download/binance.py` | спот, доходности, модель дисперсии, минута внутри часа |
| Binance перп 1 мин + премия | `data/raw/perp` | `src/download/perp.py` | **базис** BRTI/Binance (сейчас не измеряется: каталога нет) |
| Фандинг 8 ч | `data/raw/funding` | `src/download/funding.py` | плечо кэрри, ставки |
| Deribit: DVOL и сделки опционов | `data/raw/deribit` | `src/download/deribit.py` | улыбка IV, сравнение с лесенкой |
| Polymarket дневные лесенки | `data/raw/polymarket` | `src/download/polymarket.py` | кросс-веню (Kalshi против Polymarket) |
| Kalshi часовые лесенки KXBTCD | `data/raw/kalshi_kxbtcd_60m` | `src/download/kalshi.py` | **основная лента крыла**: книги по минутам, июль–октябрь |
| Макро-календарь США | `data/manual/us_macro_calendar.csv` | `src/download/macro.py` | гейт «не торговать в релиз» |
| Ноябрьские книги (живые) | `data/raw/wing_gap_candles` | `live.py` (логгер) | единственный live-период; **не докачивается** |

Всё это умеет вызывать один вход — `src/download/update.py`. Он же печатает диагностику.

```bash
cd ~/quant_research
python -m src.download.update --audit      # или: python src/download/update.py --audit
```

Запуск **без аргументов** (например, зелёной кнопкой в IDE) ничего не качает: он печатает ту же диагностику и
подсказку. Чтобы начать загрузку, нужен явный `--all` или `--only …` — случайный клик «Run» не должен
запускать скачивание всех источников.

Строки с `gap days > 0` — это то, что отстало; в колонке `command` написано, что запускать.

## 2. Порядок докачки

### Шаг 0. Окружение (один раз)

```bash
python3.11 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m unittest discover -s tests -p "test_*.py"     # 67 тестов, 1 требует pytest — это нормально
```

### Шаг 1. Быстрое и свежее (5–20 минут)

```bash
python -m src.download.update --only binance,funding,deribit,macro
```

Спот и фандинг — это то, без чего модель дисперсии не считается на текущую дату; DVOL нужен для сравнения
с лесенкой; макро-календарь закрывает дыру в 42 дня. Все четыре источника идемпотентны: существующие файлы
перезаписываются, ничего не дублируется.

### Шаг 2. Kalshi — самое долгое, делать в два приёма

Сначала последние недели (это то, что нужно для текущей оценки, — 10–30 минут):

```bash
python -m src.download.update --only kalshi --since 2026-10-20
```

Потом — вся история в фоне (≈80 с на день, ≈50 запросов на день, месяц ≈ 40 минут):

```bash
mkdir -p logs
nohup python -m src.download.update --only kalshi --since 2026-01-01 > logs/kalshi_backfill.log 2>&1 &
tail -f logs/kalshi_backfill.log
```

Прерывание не портит данные: каждый день — отдельный файл, повторный запуск продолжает с того места.
Не гоняйте два процесса одновременно: `backfill.py`/`daily_update.py` держат lock, а прямой вызов
`update.py` — нет.

### Шаг 3. Перпетуал (базис)

```bash
python -m src.download.update --only perp --build
```

Это единственная докачка, которая добавляет **новый вид данных**, а не ещё те же строки: без цен перпетуала
базис BRTI−Binance измерить нельзя, а именно он — кандидат в сигнал (идея 42 в `PROFIT_IDEAS_2026_11.md`).

### Если пишет `No module named 'config'`

Это значит, что файл запущен как скрипт из другой рабочей папки, и Python положил в `sys.path` каталог
`src/download/`, а не корень проекта. С 26.11 оба способа работают:

```bash
python -m src.download.update --audit          # из корня проекта
python src/download/update.py --audit          # прямой запуск файла
```

Внутри файлов `src/download/*.py` для этого стоит трёхстрочный bootstrap (`if __package__ in (None, "")`),
который добавляет корень проекта в путь до `import config`. Если вы запускаете из IDE — выставьте Working
directory = корень репозитория и интерпретатор = `.venv/bin/python` (`\.venv\Scripts\python.exe` на Windows);
оба условия теперь необязательны, но с ними любые скрипты проекта ведут себя одинаково.

### Шаг 4. Пересобрать и перепроверить

```bash
python -c "from studies.wing_panel import build; build(force=True)"
python -m studies.wings_sleep
python -m studies.wings_alpha
python -m studies.wings_ten
python -m src.download.update --audit
```

Панель кэшируется в `data/interim/wing_panel.parquet`, поэтому после докачки обязательно `force=True`.

## 3. Что докачать нельзя (и почему это важнее остального)

| чего нет | почему нельзя | что делать |
|---|---|---|
| Ноябрьские книги до 8 ноября и пропущенные часы 07–10 UTC | логгер писал только то, что успел | только вперёд: поднять `live.py` и не давать машине спать |
| Глубина стакана (размеры на уровнях) | Kalshi отдаёт свечи, а не историю книги | писать снимки **сейчас**: без них не измерить ни adverse selection (T2/T8), ни реальную ёмкость |
| Секундные тики BRTI | историю индекса задним числом не отдают | писать самим; без них не проверить арифметику расчётного среднего (V07) |
| Исполнение мейкерских заявок | в свечах нет очереди | писать книгу + свои заявки, тогда будет fill rate |

Это и есть ответ на «что качать»: **самое ценное — не история, а то, что пишется вперёд**. История Kalshi
перекачиваема в любой момент, а живая книга — нет.

## 4. Подготовка ноутбука

### 4.1 Сон — главный враг

Нужны три вещи: питание, запрет сна, автозапуск.

**Windows (PowerShell, от администратора один раз):**

```powershell
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 15
powercfg /change disk-timeout-ac 0
powercfg /requests                      # кто сейчас держит машину; пусто — никто не держит
```

**macOS:**

```bash
sudo pmset -a sleep 0 disksleep 0 hibernatemode 0
pmset -g assertions                     # что мешает сну
caffeinate -dimsu &                     # держать сон выключенным, пока живёт процесс
```

**Linux:**

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target
systemd-inhibit --what=idle:sleep --why="live logger" sleep inf &
```

В коде это уже сделано: `src/runner.keep_awake()` теперь ставит инхибитор на всех трёх ОС
(`SetThreadExecutionState` / `caffeinate -i -m -w <pid>` / `systemd-inhibit`), а `src/download/update.py`
вызывает его сам. Проверка: `python -c "from src import runner; print(runner.keep_awake())"`.
Выключить: `runner.keep_awake_off()`.

Важно: инхибитор не спасает от закрытой крышки на macOS (это сон по событию, а не по таймауту) — крышку
держать открытой или использовать `caffeinate -s` при питании от сети.

### 4.2 Планировщик — чтобы данные писались без вас

| ОС | что | команда |
|---|---|---|
| Windows | задача каждые 10 минут | `schtasks /create /tn btcvol-live /tr "C:\...\.venv\Scripts\python.exe C:\...\live_once.py" /sc minute /mo 10 /rl highest /f` |
| macOS | launchd | `~/Library/LaunchAgents/com.btcvol.live.plist` с `StartInterval` 600 и `RunAtLoad` true, затем `launchctl load -w …` |
| Linux | systemd user timer | `systemctl --user enable --now btcvol-live.timer` (готовые юниты — в `deploy/server/`) |

Ежедневная синхронизация истории: `python daily_update.py` (он сам держит lock, пишет логи и пересобирает
таблицы). Ставьте её на 06:20 UTC — это после расчёта 05:00 UTC и до европейского утра.

### 4.3 Диск, память, сеть

* Данные растут на ~1–1.5 ГБ в месяц (сейчас `data/` ≈ 300 МБ без `raw/binance`). 20 ГБ свободного места
  хватает на годы; 5 ГБ — минимум, ниже начинают сыпаться записи панели.
* RAM: 8 ГБ достаточно (панель 3.5 млн строк × 20 колонок ≈ 600 МБ, все исследования — минуты).
* Сеть: не чаще 4–5 запросов в секунду к одному хосту; `update.py` ставит `min_interval=0.25`.
  Kalshi за CloudFront отдаёт 429 при агрессии — тогда просто повторить позже, ничего не теряется.

### 4.4 Git-гигиена

* **Важно:** в этом репозитории версионируется и код, и данные (`.gitignore` так и говорит, и в git уже
  лежит 6 806 файлов `data/raw`, сам клон — 857 МБ). Значит докачанные файлы появятся в `git status` как
  сотни мегабайт. Варианта два: (а) держать как есть — воспроизводимость полная, но клон пухнет;
  (б) добавить `data/raw/kalshi*/` и `data/raw/binance/` в `.gitignore` и хранить их локально — тогда
  репозиторий остаётся лёгким, но у клона не будет ленты без отдельной докачки. Решать вам; в `results/`
  идут только CSV/MD исследований в любом случае.
* Перед длинной сессией: `git pull --ff-only`, после — `git add -A && git commit` с числами в сообщении.
* Исследования детерминированы (сиды в бутстрэпе фиксированы), поэтому повторный прогон должен давать те же
  CSV — это дешёвая проверка, что ничего не «поехало».

### 4.5 Мониторинг

```bash

tail -f logs/lab_$(date +%Y%m%d).log         # живой логгер
```

## 5. Имеет ли смысл докачивать историю: расчёт мощности

Считаем по факту, а не на глаз (1 контракт, P&L на час, `results/studies/wings_ten_bootstrap.csv`):

| правило | период | часов | ¢/час | σ на час | сколько часов нужно для t=2 при эффекте 2¢ |
|---|---|---|---|---|---|
| W04 (6–10¢, 15–30 мин) | тест сен–окт | 920 | +2.57 | 20.9¢ | **435** |
| W04 | ноябрь | 120 | −5.64 | 34.1¢ | 1 165 |
| W03 (10–20¢, 5–15 мин) | тест сен–окт | 328 | +3.33 | 30.1¢ | 907 |
| W03 | ноябрь | 51 | −5.80 | 40.2¢ | 1 613 |

Что из этого следует:

* **По июлю–октябрю данных уже с избытком**: 920 часов при нужных 435 — то есть точность оценки
  ограничена не объёмом, а тем, что эффект, судя по всему, зависит от режима.
* **Ноябрь мал**: 120 часов, чтобы поймать −5.6¢ нужно ~1 165. Поэтому «в ноябре не работает» — это пока
  отсутствие доказательства работы, а не доказательство поломки. Ещё 2–3 месяца живой ленты закроют и это.
* **Чем даст докачка истории**: интервал W04 на тесте сейчас [1.20; 3.82]¢/час; три дополнительных месяца
  (~2 100 часов) сузят его примерно до ±0.7¢ вместо ±1.3¢. Полезно, но это уточнение уже известного, а не
  новая альфа.
* **Чего не даст вообще**: ответа на вопрос «почему в ноябре минус». На него отвечают не месяцы, а
  (а) глубина стакана (кто сдаёт крыло и по какой цене), (б) базис и фандинг (режим), (в) макро-календарь.

**Вывод.** Докачивать стоит в таком порядке: живая книга с размерами → перпетуал (базис) → Kalshi-история
до сегодня → макро. Первые два пункта дают новые данные, третий — только больше тех же.
