# Докачка данных и подготовка ноутбука под поиск альфы

Короткий ответ на три вопроса:

1. **Докачивать — да, но не всё подряд.** Порядок важности: (а) свежие часовые лесенки Kalshi,
   (б) спот + фандинг + DVOL до сегодняшнего дня, (в) перпетуал (без него базис не измерить), (г) макро-календарь.
   Ноябрьскую ленту и глубину стакана **докачать нельзя** — они пишутся только вперёд.
2. **Ноутбук готовить надо, но не ради скорости.** Главное — не дать машине спать и не потерять живую ленту;
   всё остальное (venv, планировщик, логи) — это полчаса работы.
3. **Имеет ли это смысл?** Как «ещё данных → ещё альфы» — почти нет: мощности уже хватает (см. §8),
   узкое место — исполнение и устойчивость эффекта, а не объём истории. Как «не потерять живые данные,
   которых потом не будет» — да, и это единственная необратимая часть.

## 1а. Обновить код за секунды (вместо архива на 350 МБ)

В репозитории рядом лежат вещи очень разной природы: **~2 МБ кода** (`src/`, `studies/`, `tests/`, `docs/`)
и **~375 МБ уже скачанных данных** (`data/raw`, `data/interim`, `results/*.parquet`). Архив с GitHub тянет
всё вместе, поэтому после каждой правки вы качаете и распаковываете сотни мегабайт данных, которые у вас
уже есть и которые всё равно берутся не из git, а с бирж.

`scripts/get_code.py` качает только код. Три способа запустить одно и то же:

- **двойной клик** по `update_code.bat` в корне папки (Windows) — «одна кнопка»: сам находит
  `.venv\Scripts\python.exe`, печатает список изменённых файлов и ждёт нажатия клавиши;
- `./update_code.sh` — то же для macOS/Linux;
- из консоли:

```bash
python scripts/get_code.py --dry-run     # что изменилось бы, ничего не пишется
python scripts/get_code.py               # обновить (ветка main)
python scripts/get_code.py --branch arena/d0527b61-quant-research   # другая ветка
python scripts/get_code.py --http        # без git: через GitHub API (только изменённые файлы)
```

Что внутри:

- **git-путь (по умолчанию, если git установлен).** Забирается только дерево ветки
  (`git fetch --depth 1 --filter=blob:none`, ~0,5 МБ), затем пишутся **только те файлы, что отличаются** —
  сравнение идёт по git-хешу блоба (`sha1("blob <len>\0" + содержимое)`), поэтому «уже актуально»
  определяется точно, без индекса и без `git checkout`: содержимое берётся объектом (`git cat-file blob`)
  и пишется байт-в-байт. Это же снимает windows-специфику — CRLF-преобразования и записи в индекс, на
  которых `git checkout` в папке из ZIP может отказать. Работает и в распакованной из ZIP папке: скрипт
  один раз делает `git init` и запоминает remote, дальше это 0,5–5 секунд на запуск.
  Что мы записали в прошлый раз — лежит в `.code_sync.json`; по нему же скрипт отличает вашу правку от
  свежего изменения на GitHub и отказывается затирать вашу, пока нет `--force`.
- **http-путь (`--http`, если git нет).** Один запрос за деревом файлов, потом параллельно (8 потоков)
  только изменённые файлы с `raw.githubusercontent.com`, с fallback на contents API; каждый файл проверяется
  по хешу.
- **`data/raw`, `data/interim`, `results/*.parquet`, `reports/` не скачиваются никогда** — это данные, их
  источник — биржи, а не git. Из `results/` берутся только текстовые отчёты `results/studies/*.md`.

Замеры на реальном репозитории: первый прогон — **48–50 с, 160 файлов, 2,1 МБ** (против ~350 МБ архива),
повторный прогон без изменений — **0,5 с**, после одной моей правки (11 файлов) — **4–5 с**.
Локальные правки скрипт не затирает: если файл изменён вами, он откажется и попросит `--force`.

Если что-то пошло не так, скрипт теперь печатает **stderr самого git** и выходит с кодом 1, ничего не
записав (раньше ошибка `git checkout` приходила без текста и выглядела загадочно). Полезное:

- `fatal: couldn't find remote ref` — опечатка в `--branch`;
- отказ по сертификату (корпоративный прокси) — `QRR_CA_BUNDLE=C:\certs\ca.pem`;
- если git ведёт себя странно в этой папке — `python scripts/get_code.py --http` (GitHub API вместо git,
  тот же список файлов, проверка по хешу).

Ветка: по умолчанию `main`, но чужие ветки тоже можно — `--branch arena/d0527b61-quant-research`
(или переменные окружения `QRR_REMOTE` / `QRR_BRANCH`). Если ноутбук за корпоративным прокси и `https`
ругается на сертификат — укажите файл CA: `QRR_CA_BUNDLE=/path/to/ca.pem python scripts/get_code.py`.

## 2. Порядок докачки

### Одной командой (рекомендуется)

**Двойной клик по `scripts\download_all.bat` — всё.** Никаких ключей, ничего печатать не нужно. Окно
остаётся открытым, в нём построчно видно, что происходит прямо сейчас.

Тот же смысл одной командой (если удобнее из PowerShell):

```powershell
python scripts/download_all.py             # качает в этом окне, прогресс построчно
python scripts/download_all.py --dry-run   # только план: чего не хватает и сколько это часов
python scripts/download_all.py --verify    # только проверка: что уже лежит на диске
python scripts/download_all.py --status    # итог прошлого прогона, без закачки
python scripts/download_all.py --background  # уйти в фон, окно можно закрыть
```

Что скрипт делает сам, по шагам (это и есть ответ на «сделай уже нормально»):

1. **Ищет и останавливает забытые закачки прошлых запусков.** Находит процессы python, которые запускают
   загрузчик (`download_all.py`, `src.download.update`, `src.download.kalshi`, `binance_1s`, `backfill.py`,
   …), печатает их pid и командную строку и гасит. Два процесса, пишущих одни и те же файлы, — это и лишний
   нагрев, и риск мусора в данных. `--no-kill` оставляет их в живых (если вы нарочно запустили второй).
   `live.py` и исследования под это правило не попадают никогда.
2. **Печатает план**: чего не хватает по каждому источнику и сколько это займёт часов.
3. **Качает по порядку** — дешёвое сначала, Kalshi последним: binance 1m → funding → perp → deribit →
   polymarket → macro → kalshi → (по флагу) binance_1s.
4. **Пересобирает таблицы** — и предупреждает об этом отдельной строкой, потому что это единственный шаг,
   который действительно греет процессор.
5. **Проверяет результат** — таблица «последние данные / отставание, дни» по всем источникам и вердикт
   `всё скачиваемое — свежее` либо список отстающих.

Темп скрипт держит сам: общий адаптивный лимитер (на 429 ждут все потоки, пауза растёт и сама спадает),
изоляция сбоев (падает источник — остальные качаются; падает день — остальные дни качаются).
Отчёт каждого прогона: `logs/download-<дата>/summary.md`.

### Как следить за прогрессом

Если запускали двойным кликом, прогресс и так идёт в окне. Из другого окна:

```powershell
python scripts/download_all.py --status      # один экран: идёт ли, какой источник, сколько суток, когда конец
python scripts/download_all.py --watch       # то же, само обновляется каждые 15 с (--watch 5 — чаще)
Get-Content logs\download-*\run.log -Wait -Tail 20    # живой хвост журнала, если хочется видеть всё
```

`--status` разбирает журнал, а не гадает, и печатает примерно такое:

```
download-20261127-120000 — идёт, 1.2 ч
  сейчас: kalshi (с 12:03:05)
  Kalshi: 83/211 суток (39%), 31400 запросов (9.0/с), пауза 0.10 с, 429: 3, осталось ~1.5 h, упало дней: 2
  готово: binance 3.1 мин, funding 0.2 мин, perp 8.4 мин, deribit 0.6 мин, polymarket 0.4 мин
  запросов всего: 31400, 429: 12
  журнал: …/run.log
```

Как это читать:

- **`сейчас: <источник>`** — что качается прямо сейчас; время в скобках — когда источник начался.
- **`N/M суток (P%)`** — прогресс Kalshi внутри текущего запуска. Одна сутки = 15–90 с, так что число
  растёт заметно.
- **`осталось ~X`** — ETA по фактической скорости, а не по обещаниям; на 429 он честно увеличится.
- **`упало дней: N`** — эти дни не скачались (таймаут, 429 после всех попыток). Ничего не потеряно:
  повторный запуск той же команды подберёт только их.
- **`429: N`** — сколько раз биржа просила притормозить; скрипт сам расширял паузу и продолжал.
- **`идёт / завершён / остановлен`** — «остановлен» означает, что процесс умер (или был убит): состояние
  файлов целое, просто запустите команду снова. «Забытые» прогоны видны не в `--status`, а в самом скрипте:
  он перечисляет и гасит их в самом начале каждого запуска.
- **`проверка: …`** — итог автоматического аудита после закачки: какие источники отстают больше двух дней.
- Если экран пустой в первые 30 секунд — это нормально: Kalshi печатает первую строку прогресса, когда
  закончит первые сутки.

### Что качаем, с какой гранулярностью и зачем

| источник | гранулярность | зачем |
|---|---|---|
| binance | 1 минута, 2023 → сейчас | цена, на которой сеттлятся лесенки; источник реализованной волатильности |
| funding | 8 часов | стоимость удержания, режимы рынка |
| perp | 1 минута + базис | **не было ни разу**: перп, базис, связь со спотом |
| deribit | DVOL 1 час + сделки в окне снимка | подразумеваемая волатильность, с которой сравниваем лесенку |
| polymarket | дневные лесенки | второй рынок того же вопроса, для сверки |
| macro | календарь | часы релизов — гейт для W03/W04 |
| kalshi | свечи за **весь час** события, все страйки события одной пачкой | 6× больше строк и 8× меньше запросов: видно, что происходит до экспирации |
| binance_1s | **1 секунда** (по флагу `--one-second`) | сеттлмент (среднее 60 печатей BRTI в последнюю минуту) и исполнение |

Два важных следствия:

1. **Kalshi теперь в 6 раз подробнее и это почти бесплатно.** У `/historical` один запрос отдаёт свечи одного
   страйка за весь окно, сколько бы минут мы ни просили. Поэтому `--kalshi-minutes 60` (по умолчанию) даёт
   весь час вместо первых 10 минут за те же ~400 запросов на архивные сутки. Данные за 2026-07-01 … 2026-10-27
   в этом формате уже лежали в `data/raw/kalshi_kxbtcd_60m`, но пайплайн читал другую папку с 10-минутными
   свечами — теперь `kalshi.build_interim()` читает **обе** и оставляет самую подробную копию по
   `(ticker, end_ts, event)`. Панель сразу получает 3,77 млн строк вместо ~1,5 млн, без единого нового запроса.
2. **Секундные свечи — отдельный, тяжёлый датасет.** Один день = 86 400 строк (~2 МБ zip), месяц ~50 МБ.
   Поэтому они по флагу и не попадают в git (`data/raw/binance_1s/` в `.gitignore`): это кэш, который можно
   восстановить с биржи в любой момент.

Окно Kalshi по умолчанию — с **2026-01-01**: до 18.03.2026 у биржи была другая сетка страйков ($250 вместо
$100), то есть другой контракт. Всё более раннее — отдельной командой `--kalshi-since 2024-12-12` (≈34 тыс.
запросов, 1–9,5 ч в зависимости от того, какую паузу терпит биржа).

### Шаг 1а. Сколько стоит сутки Kalshi и почему это больше не 400 запросов

Одна календарная дата — 24 события, по одному в час. На каждое событие **два запроса**: список страйков
(`/markets` или `/historical/markets`) и **все его страйки одной пачкой** — `GET /series/KXBTCD/events/<событие>/
candlesticks` отдаёт `market_tickers` + `market_candlesticks` (массив свечей на каждый страйк), живой это
рынок или архивный; выше 5000 свечей ответ пагинируется через `adjusted_end_ts`. Итого ~48 запросов на сутки
вместо ~400 «по одному тикеру». Если этот эндпоинт когда-нибудь отвалится, код сам откатится на старую схему
(один запрос на страйк) — день не потеряется, просто пойдёт в 8 раз медленнее.

Скорость задаёт **не** число потоков, а пауза между запросами: все потоки делят один лимит `--min-interval`.
Узкое место — вежливость к бирже, поэтому ориентиры считаются по запросам в секунду:

| что качаем | запросов | 1/с (0,8–1,0 с паузы) | 5/с (0,2 с) | 10/с (0,1 с) |
|---|---|---|---|---|
| сутки (~48) | 48 | ~1 мин | ~10 с | ~5 с |
| окно 2026-01-01 … сегодня (211 суток) | ~10 тыс. | ~2,8 ч | ~35 мин | ~17 мин |
| весь архив с 2024-12-12 (~715 суток) | ~34 тыс. | ~9,5 ч | ~2 ч | ~1 ч |

Реальная пауза обычно сама подстраивается: на 429 лимитер расширяет промежуток, после чистых ответов
сужается обратно к `--min-interval`. В строке прогресса теперь видно и то и другое:

```
kalshi: 12/211 days done, 3.5 min elapsed, 140 requests (0.7/s), gap 1.20 s, 429: 41, ETA 2.1 h, 0 failed
```

`gap 1.20 s` при `429: 41` — это не поломка: биржа просит притормозить, скрипт притормаживает. Ускорять
надо не паузу (уменьшение `--min-interval` только добавляет 429), а число запросов: именно это и сделал
переход на пачку по всему событию.

### Что показывает проверка эндпоинтов (и почему это важно)

Первый прогон каждой закачки Kalshi начинается с проверки на одном реальном архивном событии:

```
kalshi: проверка на KXBTCD-26NOV1712 (архив): event — нет, batch — нет, ticker — да
kalshi: значит каждая пара «событие + страйки» стоит ~18 запросов; сутки ≈ 430 запросов, способ: по одному страйку (архив)
```

Три уровня, от дешёвого к дорогому:

| уровень | запросов на событие | что это |
|---|---|---|
| `event` | 1 | все страйки события одной пачкой (`/series/…/events/…/candlesticks`) |
| `batch` | 1 на 50 страйков | батч живого рынка (`/markets/candlesticks`) |
| `ticker` | по одному на страйк | архивный `/historical/markets/{ticker}/candlesticks` — в 8–20 раз дороже |

Работающий уровень выбирается сам, мёртвый отключается после трёх пустых ответов (а не стоит по запросу на
каждое событие). Отсюда же берётся ETA: при `event` — 60 запросов на сутки, при `ticker` — 430. Поэтому
`0/212 суток` через 5 минут при 850 запросах означает не «зависло», а «идёт пострайковый путь»: сутки стоят
~430 запросов, весь бэклог — ~100 тыс., при 3 запросах/с это ~9 часов. Строка прогресса теперь пишет и способ:

```
kalshi: 0/212 days done, 4.6 min elapsed, 851 requests (3.1/s), gap 0.21 s, 429: 61, пострайково 57/5088 событий, ETA 65 min, 0 failed
```

### Все исследования одной командой

```powershell

python scripts/study_all.py --only wings_sleep,wings_alpha   # только эти
python scripts/study_all.py --status     # итог прошлого запуска
```

Что делает: пересобирает панель крыльев, если её кэш старше свежих свечей; запускает **каждое исследование
отдельным процессом** (падение одного не мешает остальным, таймаут 45 мин); печатает прогресс построчно;
пишет `logs/studies-<дата>/summary.md` — что прошло, что нет и **почему**, сколько заняло, какие файлы в
`results/` и `reports/` обновились, плюс последние строки вывода каждого исследования.

Причины сбоев не угадываются, а берутся из самого лога и подписываются по-человечески:

| подпись | что значит |
|---|---|
| `нет данных: <путь>` | нужен датасет, которого нет на диске (например, ленты KXBTC15M) |
| `нет пакета: <имя>` | `pip install <имя>` (в requirements добавлен `tabulate`) |
| `не импортируется: ...` | исследование не запускалось: его модуль не импортируется (синтаксис, версия pandas, пакет) — видно за 15 секунд до старта, а не через час |
| `убит (память)` | процесс убит системой: закройте браузер, запустите это исследование через `--only` |
| `нет данных в окне` | данные есть, но не в том окне, которое нужно этому исследованию (в подписи — чего именно не хватило) |
| `ошибка: ...` | настоящая ошибка в коде, целиком — в логе исследования |

**Чего не должно быть в этом списке.** `Usecols do not match columns` — это не «нет данных» и не повод
перекачивать: так выглядели файлы-маркеры `*.csv.dense` («этот день перекачан с фильтром по страйкам»),
которые попадали под маску `*.csv*`, которой изучения ищут свечи. Теперь маркеры называются `<дата>.dense`,
старые переименовываются на старте `study_all`, а чтение сверяет заголовок файла и пропускает всё, что не
лесенка (`studies/ladders.py`). Так же молча пропускаются недописанные файлы — с одной строкой в логе.

Загрузчики (`wing_gap_download`, `wing_forecast_settlements`, `quant_inputs`) в список исследований **не
входят** — они качают данные, им место в `download_all`.

`wings_maker` — самое долгое исследование набора (сетка 48 точек × полный реплей пути каждой заявки):
11.7 мин на 119 днях архива, на полном архиве ждите ~25–30 мин, поэтому оно помечено «тяжёлым» и
пропускается в `--no-heavy`. Остальные проходят за секунды-минуты.

### Как не тратить вечер на один прогон

Полный набор — это 80 минут, и гонять его после каждой правки бессмысленно. Скрипт устроен так, чтобы
повторный запуск стоил секунды:

| что нужно | команда | сколько |
|---|---|---|
| только одна группа | `study_all.bat --group крылья` | минуты, а не час |
| только конкретные | `study_all.bat --only wings_sleep,wings_alpha` | ~1 мин |
| быстро, без ML и опционов | `study_all.bat --no-heavy` | ~15 мин |
| пересчитать всё заново, даже если ничего не менялось | `study_all.bat --rerun` | полные 80 мин |
| только посмотреть, что будет | `study_all.bat --dry-run` | секунды |
| итог прошлого прогона | `study_all.bat --status` | секунды |

**Пропуск неизменного.** Перед стартом считается отпечаток: версия кода (`studies/`, `src/`, `scripts/`) плюс
все файлы `data/raw`, `data/lab`, `data/lit` (путь, размер, время изменения). Исследование, которое прошло
под этим же отпечатком, пропускается с пометкой «пропущено (нет изменений)» — в итоге это отдельная цифра,
а не «результат». Изменились данные или код — пересчитается только затронутое.
Оговорка: если параллельно крутится `live.py`, журнал книги меняется постоянно, и пропусков не будет —
тогда честный путь `--only`/`--group`.

**Проверка импорта.** В начале прогона все исследования параллельно проверяются на импорт (~30 с на 57):
сломанный пакет, синтаксис или несовместимость с вашей версией pandas видны сразу, и такие исследования
не тратят слот. Отключается флагом `--no-check`.

**Оценки из факта.** Время берётся из медианы прошлых успешных прогонов (`data/interim/study_times.json`),
а константы реестра — только пока факта нет. Поэтому «оценка 80 мин» после первого прогона превращается
в вашу настоящую цифру, а упавшее за секунду исследование не обещает, что в следующий раз будет быстро.

**Версия кода в первой строке.** `версия кода: 396b0be, Python 3.14` — и та же строка в начале `summary.md`.
Вопрос «я точно запустил обновлённый код?» больше не требует догадок.

### Что делать после закачки

1. **Скрипт сам пересоберёт таблицы и проверит диск** (`--build`, шаг 5) и напишет `logs/download-*/summary.md`.
2. **Сбросить кэш панели крыльев** — иначе студии прочитают старые свечи: `del data\interim\wing_panel.parquet`.
3. **Прогнать исследования** (первый запуск собирает панель из новых свечей, ~1 мин; дальше — секунды):
   `python -m studies.wings_sleep` → `wings_alpha` → `wings_ten` → `wings_scale` → `wings_accuracy` →
   `wings_ml` → `wings_capacity`, итого ~7 минут. Затем `python -m src.report`.
4. **Что меняется по существу.** Панель крыльев читает `data/raw/kalshi_kxbtcd_60m`: было 4 месяца
   (июль–октябрь, ~3 тыс. часовых лесенок), станет ~11 (январь–ноябрь, ~8 тыс.). Впервые можно сделать
   честный walk-forward: обучение январь–июнь, тест июль–октябрь, холдаут 8–25 ноября (снимки уже в
   `data/raw/wing_gap_candles`), вместо обучения на двух месяцах и теста на двух.
5. **Что стало возможно только сейчас.** До этого набора мы видели лишь первые 10 минут последнего часа —
   то есть решали за 50 минут до сеттлмента. Теперь есть весь час: отклонение цены в T−5 и T−1 минуту от
   модели, залипание цены в конец часа, и объём в последние минуты для честной оценки ёмкости.

### Что ещё имеет смысл докачать (и чего это стоит)

| чего нет | зачем | цена |
|---|---|---|
| 60-минутные свечи 2026-01-01 … сейчас | путь цены в последние 50 минут перед сеттлментом (в старом 10-минутном наборе этих минут нет) | ~430 запросов/сутки на пострайковом пути, ~60 на пачке |
| `kalshi_kxbtc_60m` (range-бакеты) | второй срез того же рынка: «между K1 и K2» вместо «выше K» | отстал на месяц, 30 суток ≈ 13 тыс. запросов ≈ 1–2 ч |
| `binance_1s` (по флагу `--one-second`) | сеттлмент (среднее 60 печатей BRTI в последнюю минуту) и реалистичность исполнения | ~2 МБ и ~1 мин на сутки; 25 суток ноября ≈ 50 МБ ≈ 25 мин |
| история до 2025-12-01 (2024-12-12 …) | больше выборки | другой контракт: страйки $250 вместо $100; ~350 суток ≈ 150 тыс. запросов ≈ 13 ч — низкая ценность |
| Kalshi трейды (`/markets/trades`) | настоящие исполнения вместо объёмов из свечей — для capacity-лесенки | десятки тысяч запросов даже на 60 суток, не начинали |
| стакан Kalshi | исторической раздачи нет, только live-снимки | уже есть `live.py` |

### Почему Kalshi идёт медленно и что из этого следует

Три числа задают время бэклога, и только третье зависит от кода:

1. **Запросов на сутки.** Архивные свечи Kalshi отдаёт только по одному страйку (`/historical/markets/…`),
   пачки для архива нет. Значит сутки стоят `24 события × (1 список страйков + N страйков)`. Сколько именно
   страйков — видно по сетке: январь–июнь 2026 — страйки $250, в полосе ±1,5 % их ~11, это ~290 запросов
   на сутки; сентябрь–октябрь — $100, но берём каждый второй, ~20, это ~500; август — ~230.
2. **Потолок скорости площадки.** Без ключа Kalshi держит ~3 запроса/с с регулярными 429; с ключом лимит
   выше на порядок. 290 запросов на сутки при 3/с — это 96 с на сутки, при 10/с — 29 с.
3. **Порядок.** С недавнего времени сутки качаются **новыми первыми**: исследованиям нужны последние месяцы
   (и они же самые дешёвые у площадки — ещё не в архиве, отдаются пачками). Старый порядок «с начала»
   приносил нужные данные последними, спустя часы.

Отсюда честная арифметика для бэклога 2026-01-01 … сегодня (212 суток): ~65 тыс. запросов.
При 3 запросах/с — ~6 ч, при 10 — ~1,8 ч. Ускорить счётчик запросов уже нечем: полоса страйков задана
дизайном, а не ленью; урезание полосы — это уже другие данные. Единственный реальный рычаг — ключ Kalshi.

Стоимость конкретного дня печатается в его строке, так что оценку можно проверять на ходу:

```
kalshi: 2026-01-05 (6480 candle rows, 24 событий, 264 страйков → ~288 запросов, если пачка не работает)
```

### Если прилетел HTTP 429

`429 Too Many Requests` больше не смертелен:

- **429 ставит глобальный кулдаун**: паузу держат все потоки, а не только тот, что получил отказ; если сервер
  прислал `Retry-After`, ждём ровно столько (но не больше 30 с).
- **Пауза адаптивная, но без разгона.** Всплеск 429 от шести потоков расширяет промежуток **один раз**
  (в 1,25 раза, потолок 2 с), а не шесть раз подряд — именно этот разгон раньше загонял лимит в потолок, и
  закачка ползла на 0,8 запроса/с часами. После 25 чистых ответов подряд пауза сужается на 15 %.
- **Сбой дня больше не валит прогон.** День помечается как failed, остальные качаются дальше; в конце
  печатается `finished N/M days …, F failed` и список упавших дней. Файл дня либо полный, либо его нет —
  повторный запуск той же команды докачает только упавшие дни и пропустит уже лежащие: он их даже не считает
  в общем числе суток (`211 day(s) to fetch (120 already on disk)`).
- **Сеть, которая не пускает вообще (HTTP 401/403), не ретраится**: скрипт пишет одну строку и идёт дальше.
  Так сейчас с `www.bls.gov` — макро-календарь уже лежит в `data/manual/us_macro_calendar.csv`, шаг
  помечается `skipped`, а не `failed`.

### Шаг 2. Kalshi — самое долгое, делать в два приёма

Сначала последние недели (это то, что нужно для текущей оценки, — 10–30 минут):

```bash
python -m src.download.update --only kalshi --since 2026-10-20
```

Потом — вся история в фоне (≈80 с на день, ≈50 запросов на день, месяц ≈ 40 минут):

```bash

nohup python -m src.download.update --only kalshi --since 2026-01-01 > logs/kalshi_backfill.log 2>&1 &
tail -f logs/kalshi_backfill.log
```

Прерывание не портит данные: каждый день — отдельный файл, повторный запуск продолжает с того места.
Не гоняйте два процесса одновременно: `backfill.py`/`daily_update.py` держат lock, а прямой вызов
`update.py` — нет.

### Шаг 3. Перпетуал (базис)

```bash
python -m src.download.update --only perp --build
```

Это единственная докачка, которая добавляет **новый вид данных**, а не ещё те же строки: без цен перпетуала
базис BRTI−Binance измерить нельзя, а именно он — кандидат в сигнал (идея 42 в `PROFIT_IDEAS_2026_11.md`).

### Если пишет `No module named 'config'`

Это значит, что файл запущен как скрипт из другой рабочей папки, и Python положил в `sys.path` каталог
`src/download/`, а не корень проекта. С 26.11 оба способа работают:

```bash
python -m src.download.update --audit          # из корня проекта
python src/download/update.py --audit          # прямой запуск файла
```

Внутри файлов `src/download/*.py` для этого стоит трёхстрочный bootstrap (`if __package__ in (None, "")`),
который добавляет корень проекта в путь до `import config`. Если вы запускаете из IDE — выставьте Working
directory = корень репозитория и интерпретатор = `.venv/bin/python` (`\.venv\Scripts\python.exe` на Windows);
оба условия теперь необязательны, но с ними любые скрипты проекта ведут себя одинаково.

## 3. Что докачать нельзя (и почему это важнее остального)

| чего нет | почему нельзя | что делать |
|---|---|---|
| Ноябрьские книги до 8 ноября и пропущенные часы 07–10 UTC | логгер писал только то, что успел | только вперёд: поднять `live.py` и не давать машине спать |
| Глубина стакана (размеры на уровнях) | Kalshi отдаёт свечи, а не историю книги | писать снимки **сейчас**: без них не измерить ни adverse selection (T2/T8), ни реальную ёмкость |
| Секундные тики BRTI | историю индекса задним числом не отдают | писать самим; без них не проверить арифметику расчётного среднего (V07) |
| Исполнение мейкерских заявок | в свечах нет очереди | писать книгу + свои заявки, тогда будет fill rate |

Это и есть ответ на «что качать»: **самое ценное — не история, а то, что пишется вперёд**. История Kalshi
перекачиваема в любой момент, а живая книга — нет.

## 4. Подготовка ноутбука

### 4.1 Сон — главный враг

Нужны три вещи: питание, запрет сна, автозапуск.

**Windows (PowerShell, от администратора один раз):**

```powershell
powercfg /change standby-timeout-ac 0
powercfg /change hibernate-timeout-ac 0
powercfg /change monitor-timeout-ac 2      # экран гаснет через 2 минуты — это НЕ сон, качалке всё равно
powercfg /change disk-timeout-ac 0
powercfg /setacvalueindex SCHEME_CURRENT SUB_BUTTONS LIDACTION 0   # закрытая крышка: ничего не делать
powercfg /setactive SCHEME_CURRENT
powercfg /requests                      # кто сейчас держит машину; пусто — никто не держит
```

Смысл в двух разных вещах, которые легко перепутать:

- **Экран погасить — можно и нужно.** Гашение экрана, блокировка (Win+L) и переход в «спящий экран» процесс
  не останавливают. `monitor-timeout-ac 2` гасит подсветку, вычисления продолжаются.
- **Сон машины — нельзя.** Его держит инхибитор (`keep_awake`, `SetThreadExecutionState`), но только от
  простоя. Закрытая крышка — отдельное событие: её надо перевести в «ничего не делать» строкой
  `LIDACTION 0` выше (или оставить крышку открытой). Ноутбук — на зарядку: от батареи Windows всё равно
  уйдёт в сон по своему плану.

**macOS:**

```bash
sudo pmset -a sleep 0 disksleep 0 hibernatemode 0
pmset -g assertions                     # что мешает сну
caffeinate -dimsu &                     # держать сон выключенным, пока живёт процесс
```

**Linux:**

```bash
sudo systemctl mask sleep.target suspend.target hibernate.target
systemd-inhibit --what=idle:sleep --why="live logger" sleep inf &
```

В коде это уже сделано: `src/runner.keep_awake()` теперь ставит инхибитор на всех трёх ОС
(`SetThreadExecutionState` / `caffeinate -i -m -w <pid>` / `systemd-inhibit`), а `src/download/update.py`
вызывает его сам. Проверка: `python -c "from src import runner; print(runner.keep_awake())"`.
Выключить: `runner.keep_awake_off()`.

Важно: инхибитор не спасает от закрытой крышки на macOS (это сон по событию, а не по таймауту) — крышку
держать открытой или использовать `caffeinate -s` при питании от сети.

### 4.2 Планировщик — чтобы данные писались без вас

| ОС | что | команда |
|---|---|---|
| Windows | задача каждые 10 минут | `schtasks /create /tn btcvol-live /tr "C:\...\.venv\Scripts\python.exe C:\...\live_once.py" /sc minute /mo 10 /rl highest /f` |
| macOS | launchd | `~/Library/LaunchAgents/com.btcvol.live.plist` с `StartInterval` 600 и `RunAtLoad` true, затем `launchctl load -w …` |
| Linux | systemd user timer | `systemctl --user enable --now btcvol-live.timer` (готовые юниты — в `deploy/server/`) |

Ежедневная синхронизация истории: `python daily_update.py` (он сам держит lock, пишет логи и пересобирает
таблицы). Ставьте её на 06:20 UTC — это после расчёта 05:00 UTC и до европейского утра.

### 4.3 Диск, память, сеть

* Данные растут на ~1–1.5 ГБ в месяц (сейчас `data/` ≈ 300 МБ без `raw/binance`). 20 ГБ свободного места
  хватает на годы; 5 ГБ — минимум, ниже начинают сыпаться записи панели.
* RAM: 8 ГБ достаточно (панель 3.5 млн строк × 20 колонок ≈ 600 МБ, все исследования — минуты).
* Сеть: не чаще 4–5 запросов в секунду к одному хосту; `update.py` ставит `min_interval=0.25`.
  Kalshi за CloudFront отдаёт 429 при агрессии — тогда просто повторить позже, ничего не теряется.

### 4.4 Git-гигиена

* **Важно:** в этом репозитории версионируется и код, и данные (`.gitignore` так и говорит, и в git уже
  лежит 6 806 файлов `data/raw`, сам клон — 857 МБ). Значит докачанные файлы появятся в `git status` как
  сотни мегабайт. Варианта два: (а) держать как есть — воспроизводимость полная, но клон пухнет;
  (б) добавить `data/raw/kalshi*/` и `data/raw/binance/` в `.gitignore` и хранить их локально — тогда
  репозиторий остаётся лёгким, но у клона не будет ленты без отдельной докачки. Решать вам; в `results/`
  идут только CSV/MD исследований в любом случае.
* Перед длинной сессией: `git pull --ff-only`, после — `git add -A && git commit` с числами в сообщении.
* Исследования детерминированы (сиды в бутстрэпе фиксированы), поэтому повторный прогон должен давать те же
  CSV — это дешёвая проверка, что ничего не «поехало».

| W04 | ноябрь | 120 | −5.64 | 34.1¢ | 1 165 |
| W03 (10–20¢, 5–15 мин) | тест сен–окт | 328 | +3.33 | 30.1¢ | 907 |
| W03 | ноябрь | 51 | −5.80 | 40.2¢ | 1 613 |

Что из этого следует:

* **По июлю–октябрю данных уже с избытком**: 920 часов при нужных 435 — то есть точность оценки
  ограничена не объёмом, а тем, что эффект, судя по всему, зависит от режима.
* **Ноябрь мал**: 120 часов, чтобы поймать −5.6¢ нужно ~1 165. Поэтому «в ноябре не работает» — это пока
  отсутствие доказательства работы, а не доказательство поломки. Ещё 2–3 месяца живой ленты закроют и это.
* **Чем даст докачка истории**: интервал W04 на тесте сейчас [1.20; 3.82]¢/час; три дополнительных месяца
  (~2 100 часов) сузят его примерно до ±0.7¢ вместо ±1.3¢. Полезно, но это уточнение уже известного, а не
  новая альфа.
* **Чего не даст вообще**: ответа на вопрос «почему в ноябре минус». На него отвечают не месяцы, а
  (а) глубина стакана (кто сдаёт крыло и по какой цене), (б) базис и фандинг (режим), (в) макро-календарь.

**Вывод.** Докачивать стоит в таком порядке: живая книга с размерами → перпетуал (базис) → Kalshi-история
до сегодня → макро. Первые два пункта дают новые данные, третий — только больше тех же.
