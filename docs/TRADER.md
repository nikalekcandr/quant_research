# Боевой исполнитель для Kalshi (`trader/`)

Программа, которая берёт решения лаборатории по продаже крыльев (W03–W06) и превращает их в заявки на Kalshi:
сначала **в тени** (только чтение настоящего стакана), потом **на демо-бирже** (фальшивые деньги), и только после
проверок — **на реальном счёте**. Теория исполнения — `docs/EXECUTION.md`, сами правила — `STRATEGIES.md`.

## 1. Как устроено

```
лаборатория (lab_daemon.py, 24/7)                исполнитель (python -m trader run)
  правила W03–W06 решают ── intents.jsonl ──►   1. фильтры риска и свежести
  (правила заморожены, код                       2. живой стакан production (не листинг!)
   правил не менялся)                            3. перепроверка edge по живой цене
                                                 4. размер позиции
                                                 5. заявка: shadow / demo / live
                                                 6. сверка: статус заявки, исполнения, расчёт
                                                 7. журнал data/trader/journal_<mode>.jsonl
```

Лаборатория решает, исполнитель исполняет. Это разделение сделано специально:

* правила остаются замороженными (AGENTS.md, правило 6): в лабораторию добавлена только запись решения в файл
  (`lab/intents.py`), логика правил не тронута;
* бумажный результат лаборатории и реальный результат исполнителя пишутся по одному и тому же решению, поэтому
  их можно сравнить сделка к сделке: так измеряется проскальзывание и доля исполнения;
* если исполнитель упал, лаборатория продолжает работать, и наоборот.

### Какие решения приходят из лаборатории

| Тип | Кто пишет | Что делает исполнитель |
|---|---|---|
| `take` | W03, W04 всегда; W05/W06 в минуту отката | IOC-заявка по цене не хуже решения лаборатории |
| `quote` | W05/W06 при выставлении котировки | по умолчанию игнорируется: мейкер на крыльях проигрывает (см. ниже) |
| `cancel` | W05/W06, когда котировка снята | снять заявку, учесть частичное исполнение |
| `paper_fill` | W05/W06, если бумажная котировка «исполнилась» | только запись в журнал |

В каждом решении есть справедливая цена лаборатории, порог правила (margin) и спот BTC в момент решения.

## 2. Что проверяется перед каждой заявкой

| Проверка | По умолчанию | Зачем |
|---|---|---|
| Возраст решения | ≤ 20 с | правило 7: не торговать устаревшими ценами |
| Сдвиг спота с момента решения | ≤ 20 б.п. | больше — модель уже не про этот рынок, отказ |
| Справедливая цена | пересчитывается под текущий спот | 1 б.п. спота ≈ 1¢ цены крыла за 10–30 мин до часа (см. ниже) |
| До расчётного окна | ≥ 2 мин | у Kalshi расчёт по средней BRTI за последние 60 с |
| Спред рынка | ≤ 3¢ | широкий спред — признак пустого стакана |
| Цена в стакане | ≤ цены лаборатории (+ `slippage_ticks`) | не догонять рынок |
| Edge по живой цене | fair − цена − комиссия ≥ margin правила | если преимущество исчезло, не входить |
| Одна позиция на правило и час | — | соседние страйки одного часа — одна ставка |
| Сделок в час | ≤ 2 | W03+W05 или W04+W06 — тоже одна ставка |
| Открытых позиций | ≤ 6 | общий лимит риска |
| Дневной убыток | ≤ $15 | после него — стоп до следующего дня |
| Kill switch | файл `data/trader/KILL` | снять всё и выйти |

**Пересчёт справедливой цены.** Лаборатория посчитала вероятность дешёвой стороны c при споте S₀. В её
модели c = Φ(±ln(S₀/K)/σ), отсюда σ = ±ln(S₀/K)/Φ⁻¹(c), и при текущем споте S₁ та же σ даёт новую c. Пример из
первого же live-решения 02.11 22:48: W03 решила продать YES-крыло 17¢ с edge 1,3¢. Через 5 с спот был на 5,9 б.п.
ниже, то есть в нашу пользу, а первая версия исполнителя такие решения просто отбрасывала. Теперь сдвиг в нашу
пользу увеличивает edge, а против нас уменьшает, и вход разрешается только если edge после пересчёта ≥ порога.

**Слоты.** W05 выбирает тот же страйк и сторону, что W03, а W06 — что W04 (100% общих часов на истории). Поэтому
в каждом часе два слота: «поздний» (W03/W05) и «ранний» (W04/W06), по одной позиции на слот.

**Проход по стакану.** IOC-лимит ставится на худшем уровне, где edge по пересчитанной справедливой цене ещё
≥ порога. С каждого уровня берётся ≤ 25% объёма, в пределах бюджета риска.

**Почему не мейкер.** На июльско-октябрьских свечах мейкерскую продажу крыла W03 покупают в основном тогда, когда
крыло сработает: 16,5% против 4,8%, когда не купили. «Пассивно, затем агрессивно» даёт +0,2…−0,9¢ против +3,2¢ при
немедленной продаже (`results/studies/options_wings_audit.md`). Мейкерский код остаётся (`maker_rules`), но выключен.

**Размер:** `min(max_contracts, risk_per_trade_usd / цена, 25% объёма лучшего уровня)`. При $5 на сделку и цене
0,92 это 5 контрактов. Максимальный убыток сделки равен цене × число контрактов, то есть заданным $5.

**Комиссии Kalshi:** тейкер ⌈0,07·C·P·(1−P)⌉, мейкер ⌈0,0175·C·P·(1−P)⌉ на заявку, округление вверх до цента.

### Почему IOC и post-only
* **Тейкер (W03/W04):** лимитная заявка `immediate_or_cancel` по проверенной цене. Исполнится сразу и не хуже
  лимита, остаток биржа снимет сама. Рыночные заявки не используются никогда.
* **Мейкер (W05/W06):** `post_only` + `good_till_canceled` с `expiration_ts` = минута отката. Если цена заявки
  пересекла бы стакан, биржа её отклонит, а не исполнит по худшей цене. Заявка снимается раньше, если спот ушёл
  против нас больше чем на 3 б.п. (защита от быстрого тейкера, который видит движение раньше нас).
* У каждой заявки детерминированный `client_order_id` (из id решения), поэтому повтор после сбоя сети не создаёт
  дубль: исполнитель сначала ищет заявку по этому id.
* `cancel_order_on_pause = true`: если биржа приостановит торговлю, висящие заявки снимутся.

## 3. Режимы

| Режим | Ключи | Заявки | Для чего |
|---|---|---|---|
| `shadow` | не нужны | нет | проверить, был ли бы реальный вход по цене лаборатории и на какую глубину |
| `demo` | ключ демо-биржи | на demo.kalshi.co, деньги ненастоящие | проверить подпись, заявки, отмены, сверку, расчёт |
| `live` | ключ kalshi.com | настоящие | только после этапов ниже |

**Важно про demo.** Цены и стаканы демо-биржи не совпадают с настоящими: Kalshi прямо пишет, что поведение рынков
там «может не отражать реальные». Поэтому решения проверяются по **настоящему** стакану production (как в
shadow), а заявка отправляется на демо по цене демо-стакана. P&L на демо ничего не говорит о стратегии, демо
проверяет только механику. Если на демо нет такого же тикера, решение пропускается с причиной в журнале. Опция
`demo_ignore_edge = true` разрешает тестовые заявки по 1 контракту даже когда демо-цена хуже.

Shadow-режим уже запущен на компьютере как задача лаборатории (`jobs/trader_shadow_now.py`).

## 4. Подключение демо-счёта (Windows)

1. Зарегистрироваться на **https://demo.kalshi.co** (отдельный аккаунт, данные production не подходят).
2. Профиль → API Keys → **Create New API Key**. Сохранить приватный ключ (показывается один раз) в файл,
   например `C:\Users\Administrator\kalshi\demo.pem`. Ключ не класть в папку проекта и не коммитить.
3. Задать переменные окружения (PowerShell, один раз):
   ```powershell
   setx KALSHI_DEMO_KEY_ID "<id ключа>"
   setx KALSHI_DEMO_KEY_FILE "C:\Users\Administrator\kalshi\demo.pem"
   ```
   и открыть новое окно терминала.
4. Проверка (из папки проекта):
   ```powershell
   python -m trader check --mode demo        # часы, статус биржи, баланс, есть ли KXBTCD на демо
   python -m trader test-order --mode demo   # заявка 1 контракт по 1¢, чтение, отмена
   ```
5. Запуск:
   ```powershell
   python -m trader run --mode demo
   python -m trader status --mode demo       # в другом окне: позиции, причины пропусков
   python -m trader report --mode demo       # рассчитанные сделки
   python -m trader kill                     # аварийная остановка (снимет заявки и выйдет)
   ```
Настройки лежат в `data/trader/settings.json` (создаётся при первом запуске с значениями по умолчанию).

## 5. Переход на реальные деньги: чек-лист

1. Shadow ≥ 2 недель: доля решений, где цена лаборатории реально была в стакане, ≥ 70%; средняя разница
   «цена стакана − цена лаборатории» ≤ 0,5¢.
2. Demo: ≥ 50 заявок без расхождений между журналом, `GET /portfolio/fills` и `GET /portfolio/positions`.
3. Бумажный W03–W06 к этому моменту: ≥ 150 сделок, сумма > 0 при t > 1,5, в среднем ≥ +1¢.
4. Live: `"mode": "live"` в настройках, ключ production в `KALSHI_KEY_ID` / `KALSHI_KEY_FILE`, переменная
   `KALSHI_ALLOW_LIVE=1` и флаг `--real-money`. Начать с `risk_per_trade_usd` = 1–2 и `daily_loss_limit_usd` = 5.
5. Масштаб: $100 → $1 000 только после ~200 живых сделок с проскальзыванием ≤ 0,5¢ (`docs/EXECUTION.md` §8).

## 6. Задержка и инфраструктура

* Путь «лаборатория решила → заявка на бирже»: цикл лаборатории ~7–8 с + опрос файла 1 с + стакан и заявка
  2 × 100–300 мс из Москвы. Для тейкерских W03/W04 это допустимо: решение берётся за 5–30 минут до часа,
  а цена проверяется заново перед отправкой.
* Для мейкера задержка важнее: быстрый тейкер увидит движение спота раньше нас. Правило отмены по споту
  частично защищает; дальше — сервер в США (Kalshi в us-east) и WebSocket-канал `orderbook_delta` вместо опроса.
* Компьютер не должен засыпать: ночью 29→30.10 лаборатория простояла 6 часов. В PowerShell от администратора:
  `powercfg /change standby-timeout-ac 0` и `powercfg /change hibernate-timeout-ac 0`.
